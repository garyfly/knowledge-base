# S5 · 实时通信与消息（2 周）

> 目标：理解"长连接 + 多实例广播"这件事为什么比 REST 难一个量级。
> 前端你只会 `new WebSocket()`，这周你要做的是**服务端怎么管理成千上万个连接，并在多台机器间保持一致**。

## 实战需求

**在 `kb-api` 上加实时协作能力（笔记评论 + 在线协作状态）：**

1. **WebSocket 服务**：用 `ws`（或 Socket.IO）实现连接鉴权（用 S3 的 JWT）、心跳保活、断线清理
2. **房间模型**：每个笔记一个房间；加入/离开广播；在线用户列表
3. **消息协议设计**：自定义帧格式 `{ type, id, payload }`，含 ack 机制（客户端收到确认）、错误帧、版本号
4. **广播**：同一房间内所有人收到新评论（不含发送者重复渲染问题）
5. **多实例广播**：启动 2 个 Node 实例 + Redis Pub/Sub，验证 A 实例的连接能收到 B 实例房间的消息
6. **消息可靠性**：断线重连后补发遗漏消息（用 Redis Stream 或本地队列 + 客户端 lastEventId）
7. **状态同步**：用 Redis 存房间在线状态（不是内存），进程重启后状态不丢
8. **降级方案**：WebSocket 不可用时前端如何轮询（写清接口契约）
9. **压测**：用脚本模拟 500 个并发连接持续发消息，观察内存/CPU/延迟

## 知识点与前端对照

| 知识点 | 前端视角 | 后端本周要掌握 |
| --- | --- | --- |
| WebSocket 握手 | 浏览器自动完成 | HTTP Upgrade 请求、`Sec-WebSocket-Key` 校验、握手时怎么带 token |
| 长连接成本 | 免费 | 每个连接占内存与 fd，1 万连接意味着什么；连接数与 ulimit |
| 心跳 | 没做过 | ping/pong、半开连接（网络断了但服务端不知道）怎么发现 |
| 消息协议 | 随意 JSON | 版本化、类型枚举、ack/重试、幂等、顺序性、最大帧大小 |
| 广播复杂度 | 简单 | N 个连接 × M 条消息 = 扇出；写扩散 vs 读扩散 |
| 多实例 | 单机思维 | 为什么内存里的房间列表在多实例下必然失效；Redis Pub/Sub 的角色 |
| Pub/Sub 特性 | 无 | 无持久化、无 ack、订阅者离线消息即丢；和 Stream/队列的区别 |
| 顺序与重复 | UI 层处理 | at-least-once vs exactly-once，去重键怎么设计 |
| 断线重连 | 简单重连 | 重连风暴、指数退避、抖动、服务端限流 |
| 背压 | 无 | 慢客户端导致服务端内存暴涨，必须丢消息或断开 |

## 常见坑

1. **浏览器 WebSocket 不能带自定义 Header** —— 鉴权方案要提前定：query token（会进日志）、Sec-WebSocket-Protocol、或先 HTTP 换一次性 ticket。
2. **无心跳** —— 客户端拔网线，服务端永远不知道，连接泄漏（`netstat` 会看到大量 ESTABLISHED）。
3. **`ws.send` 不做错误处理** —— 连接已关闭时发送会抛错并可能崩进程。
4. **广播循环里同步做耗时操作** —— 阻塞事件循环，所有连接一起卡。
5. **Redis Pub/Sub 当成消息队列** —— 它不持久化，订阅者不在线消息就没了。
6. **重连不退避** —— 服务端重启时所有客户端同时重连，形成自我 DoS。
7. **消息无版本** —— 前后端一改协议就全炸，从第一天就带 `v` 字段。
8. **只测单实例** —— 多实例问题一定会在上线后才发现，这周必须提前踩。

## AI 协作提示词

**协议评审：**
```text
这是我设计的 WebSocket 消息协议（贴 TS 类型 + 几个示例帧）。
请指出协议里 3 个会在真实网络环境下出问题的设计（重连、丢包、版本升级、大消息），
每条给出具体失败场景。不要给新协议，只挑问题。
```

**分布式讲解：**
```text
我的服务现在单实例用内存 Map 管理房间，要扩展到 3 个实例。
请用"消息从连接 A 到连接 B 的完整路径"逐步解释需要哪些组件，
并指出每一步可能丢消息的位置。不要给代码。
```

**出压测题给我写：**
```text
我要验证我的 WebSocket 服务在 500 并发连接下的表现。
请告诉我需要测哪 5 个指标、每个指标怎么采集、用什么工具，
以及"结果多差算不合格"的判定标准。不要写压测脚本。
```

**扮演线上事故复盘（进阶）：**
```text

列出 6 个可能的根因，按可能性排序，并给出每个根因的验证命令或日志关键词。
```
