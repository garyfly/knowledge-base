## D3 · 命令行解析 + 批量重命名

**目标**：手写参数解析，并实现带保护机制的批量重命名。

- [ ] **1. 手写参数解析器**
  - `parseArgs(argv)` → `{ command, flags, positionals }`，支持 `--key value` 与 `--flag`
  - 支持 `--help`（每个子命令各自的帮助）、未知 flag 报错、缺值时提示用法
  - 出错时 `process.exitCode = 1`（不要用 `process.exit()` 粗暴退出，先看行为差异）
- [ ] **2. 重命名核心**
  - `nb rename <目录> --pattern "*.md" --prefix "note-"`
  - **默认就是 dry-run**：只打印 `旧名 → 新名`；真执行需要 `--yes`
  - 目标已存在时跳过并警告（不能静默覆盖）
- [ ] **3. 安全护栏**
  - 执行前先全量检测目标名冲突 → 有冲突就**整体中止**，不部分执行
  - 打印汇总：将处理 N 个、冲突 M 个、跳过 K 个

**验证**
```bash
mkdir tmp && cd tmp && git init && touch a.md b.md   # 在 git 保护下做实验
pnpm dev rename ./tmp --pattern "*.md" --prefix "note-"     # 只打印
git status          # 必须干净，证明 dry-run 真的没动文件
pnpm dev rename ./tmp --pattern "*.md" --prefix "note-" --yes
git status          # 现在才看到重命名
```

**坑**
- `--prefix` 没带值 → `undefined` 参与拼接变成 `undefineda.md`，必须显式校验
- dry-run 与真执行走两条代码路径 → 迟早不一致；让真执行复用同一条"计划生成"逻辑
- 覆盖同名文件 = 数据丢失，冲突必须整体中止
- 重命名顺序影响结果（改了名之后又被 pattern 匹配到）→ 先收集完列表再统一执行

**今天的 AI 提示词**
```text
这是我的参数解析与 rename 实现（贴代码）。
请只列"用户误操作会导致文件丢失或改名错乱"的场景，最多 5 个，
每个给出触发命令（我要能照着输）和后果。不要给修复代码。
```

## D4 · 异步与并发控制（本周最重要的一天）

**目标**：理解"并发"到底并发了什么，写出可靠的并发控制器。

- [ ] **1. 实现 `runWithConcurrency`**
  - `runWithConcurrency<T, R>(tasks: (() => Promise<T>)[], limit: number): Promise<R[]>`
  - 三个硬约束：**结果顺序与输入一致**、**同时执行数 ≤ limit**、某个任务抛错时的策略明确（快速失败 or 收集全部错误，选一个并写进注释）
- [ ] **2. 用探针验证并发上限**
  - 造 20 个任务，每个 `await sleep(50)`，打印 `开始时间戳 / 结束时间戳`
  - 断言：任意时刻在跑的任务数 ≤ limit；总耗时 ≈ `ceil(20/limit) × 50ms`
- [ ] **3. 对比 `Promise.all`，用文字写出差别**
  - `Promise.all`：全部同时启动，只负责"等"
  - 你的控制器：负责"排队"
  - 两者完成时间与峰值并发各是多少，把数字写进复盘

**验证**
```bash
pnpm test            # 或用 tsx 直接跑一个 demo 脚本
# 必须能看到：空数组 → []、limit > 任务数 → 不报错、任务抛错 → 有明确行为
```

**坑**
- 用 `for` + `await` = 完全串行（不是并发）
- 用 `Promise.all` 以为"限制了并发" —— 它是并发等待器，不是并发控制器
- 任务函数抛错后没被捕获 → `UnhandledPromiseRejection`，Node 默认进程退出
- 用外层变量 `i` 捕获闭包 → 所有任务拿到同一个索引

**今天的 AI 提示词（先自己写完再看）**
```text

不要重写。请做三件事：
① 指出我的实现在"任务抛错""limit=1""任务数 0""limit 大于任务数"四种情况下各自的行为；
② 指出其中一个可能违反"结果顺序一致"的隐藏 bug；
③ 给我 4 个测试用例名（只给名字）。
```

## D5 · 流、Buffer 与背压

**目标**：亲手制造一次内存差异，把"流"从名词变成体感。

- [ ] **1. 造一个 200MB 测试文件**
  - `nb gen ./tmp/big.md --size 200MB`（或 PowerShell `fsutil file createnew` / 循环写）—— 别用编辑器生成
- [ ] **2. 两种读法的内存对比**
  - A：`await readFile(big)` → 打印 `process.memoryUsage().heapUsed / rss` 与耗时
  - B：`createReadStream` 分块累加 → 打印同样的指标与耗时
  - 结论写下来：峰值内存差多少倍？谁更快？（很可能 B 不是更快，但内存可控 —— 这个反直觉很重要）
- [ ] **3. 把流式统计接进 `count` + 处理多字节截断**
  - `nb count --stream` 走流式路径，结果与一次性读取**完全一致**
  - 说明分块时 UTF-8 字符被切断的情况，以及为什么不能直接 `chunk.toString()` 拼接

**验证**
```bash
node --max-old-space-size=256 dist/index.js count ./tmp   # 流式应能跑完，一次性读取应崩
```

**坑**
- 分块边界处 `chunk.toString()` 会把一个中文字符切坏 → 乱码
- 忘了监听 `stream.on('error')` → 文件不存在时静默失败
- 以为"流 = 更快" —— 流主要解决的是**内存上限与首字节延迟**，不是吞吐
- 统计完不释放引用（把大 Buffer 存在数组里）→ 内存照样涨

**今天的 AI 提示词**
```text
我用 createReadStream 分块统计文件字符数（贴代码）。
请解释：如果我直接对每个 chunk 调 toString() 再累加，在什么情况下结果会错？
给我一段 20 字节以内、能稳定复现该问题的十六进制内容（中文字符的 UTF-8 字节），
以及正确的处理思路。不要给完整实现。
```

## D6 · `fs.watch` 目录监听（时间不够就砍这天）

**目标**：实现 `nb watch`，并亲眼看到 `fs.watch` 的"噪音"。

- [ ] **1. 最朴素的 watch**
  - `fs.watch(dir, { recursive: true }, cb)` 打印事件类型与文件名
  - 用编辑器保存一次，**数一数**打印了几行 → 通常 2~3 行，这就是坑的来源
- [ ] **2. 去重 + 节流**
  - 按 `文件名 + 事件类型` 去重；**300ms 内的连续事件合并成一条**
  - 输出形如 `[修改] note-a.md`
- [ ] **3. 优雅退出**
  - `Ctrl+C` 时关闭 watcher、打印汇总、进程干净退出（`process.on('SIGINT')`）

**验证**
```bash
pnpm dev watch ./01\ Notes      # 路径含空格，顺便练参数引号处理
# 反复保存同一个文件 → 只应输出一条"修改"
# Ctrl+C → 无 "Watcher closed" 之后的报错，终端立刻回到提示符
```

**坑**
- 编辑器保存 = 写临时文件 + rename，所以事件必然重复
- `fs.watch` 在某些平台/路径下 recursive 不生效 → 不生效就退化为逐目录递归挂 watch
- Ctrl+C 后进程不退出 → 监听器或定时器未清理
- 文件被删除时事件里拿不到时间戳，别依赖 mtime

**今天的 AI 提示词**
```text
我在 Windows 上用 fs.watch(dir, { recursive: true }) 监听目录（贴我的代码和实际打印的事件序列）。
请解释这个事件序列里每一步对应编辑器的什么操作，
并指出我的去重/节流逻辑在"快速连续保存两次"和"文件被重命名"两种情况下是否可靠。只挑问题，不要给代码。
```
