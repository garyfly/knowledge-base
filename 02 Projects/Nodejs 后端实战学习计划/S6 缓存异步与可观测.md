# S6 · 缓存、异步任务与可观测（1 周）

> 目标：让服务从"能跑"变成"扛得住、看得见"。
> 三个关键词：**缓存**（少干活）、**队列**（别让用户等）、**可观测**（出事能查）。

## 实战需求

1. **缓存层**：
   - 给 `GET /notes/:id`、热门标签列表加 Redis 缓存（Cache-Aside）
   - 实现"写操作后精确失效"（不是 `FLUSHALL`）
   - 处理**缓存穿透**（查不存在的 id）、**击穿**（热点 key 同时过期）、**雪崩**（大量 key 同时失效）
   - 记录命中率，并演示命中/未命中时延差
2. **异步任务（BullMQ）**：
   - `POST /notes/:id/export` 立即返回 `taskId`，后台生成 Markdown 导出
   - `GET /tasks/:id` 查询任务状态（pending/active/completed/failed）与进度
   - 失败自动重试（指数退避）+ 最大重试次数 + 死信处理
   - 定时任务：每天凌晨清理 30 天前的软删除数据（BullMQ repeatable job）
   - 附件上传后异步生成缩略图（同时练习 Multer/流式上传 + 大小与类型限制）
3. **可观测性**：
   - 结构化日志（Pino）含 `traceId`、`userId`、耗时、状态码；敏感字段脱敏
   - 健康检查 `GET /healthz`（含数据库/Redis 连通性）与 `GET /readyz`
   - 关键指标：请求量、错误率、P95 延迟、队列积压、缓存命中率
   - 优雅关闭：收到 SIGTERM 后停止接新请求、等待在途请求、关闭连接池与队列
4. **压测与容量**：用 autocannon 做一次基线压测，找出第一个瓶颈并优化，复测对比

## 验收标准

- [ ] 缓存命中率可查询且 >70%（压测场景下）
- [ ] 更新笔记后立刻 GET 能拿到新值（证明失效正确，不是缓存旧数据）
- [ ] 导出任务：提交后立刻 202 + taskId；进度可查；失败能看到重试次数与最终错误
- [ ] 杀掉 worker 进程后重启，未完成任务不丢（Redis 持久化配置正确）
- [ ] `curl /healthz` 在数据库断开时返回 503（真的能反映依赖故障，不是永远 200）
- [ ] `kill -TERM` 时正在处理的请求正常返回，不出现连接重置
- [ ] 压测报告含优化前后 P95 对比，并指出瓶颈是什么、为什么
- [ ] 能解释：为什么不能用过期时间解决所有一致性问题？重试为什么必须幂等？
- [ ] 能解释：`/healthz` 与 `/readyz` 的区别，以及为什么部署时两者都要有

## 常见坑

1. **缓存了不该缓存的**（用户私有数据没带 userId 进 key）→ 串号是重大事故。
2. **先更新数据库再删缓存但删失败** —— 需要重试/延迟双删或用消息补偿；要能说清不一致窗口。
3. **`cache.del('notes:*')`** —— Redis 是单 key 删除，通配符要用 `SCAN` 或维护 key 集合。
4. **队列任务里带大对象** —— job payload 要小，只传 id 和必要参数。
5. **任务不幂等** —— 重试 = 重复执行，导出/发邮件/扣款都会出问题。
6. **Worker 和 API 同进程** —— 压测时 API 被任务拖垮，生产要分开部署。
7. **日志里打 `req.body`** —— 密码和 token 直接进日志系统。
8. **健康检查依赖太多** —— 检查数据库 + Redis 就够，别检查第三方，否则误报。
9. **SIGTERM 不处理** —— 部署时用户看到 502，你以为只是"重启一下"。

## AI 协作提示词

**缓存一致性审查：**
```text
这是我的缓存实现（贴 getOrSet 和写路径代码）。
请指出在"并发写 + 缓存过期"组合下可能出现的 3 个不一致场景，
每个场景给一个可复现的操作时序。不要给实现代码。
```

**队列设计评审：**
```text
我要用 BullMQ 实现"笔记导出"任务（贴我的 job 结构和 worker 代码）。
请检查：重试是否安全、payload 是否过大、失败是否可观测、任务是否会永久卡在 active。
最多 5 条，按严重度排序。
```

```text

```
