# 附录 B · AI 协作提示词库

> 这是一份**可直接复制**的提示词工具箱，按开发阶段分组。用法不是"从头读到尾"，而是**卡住的时候翻到对应分组，复制、填占位符、发出去**。
> 它服务的是一条铁律（本计划总纲第 6 节"学习与工作方法"）：
```text
想法 → 自己拆 (15–30min) → 写出第一版（哪怕是错的）→ 明确问题
     → 问 AI（带代码/截图 + 你的假设 + 具体问题）→ 对照改动
     → 关掉 AI 自己重写一遍 → 记录到本知识库
```

> [!important] 铁律：先自己写 → 卡住 → 问 AI → **关掉 AI 重写**
> 如果你在"卡住"之前就问 AI，你拿到的不是知识，是**一段你解释不了的代码**。它在下一周会变成技术债，在发售前会变成"这个 Bug 我不敢动"。
> 判断标准很简单：**关掉 AI 之后，你能不能自己把这段逻辑再写一遍？** 写不出来，就等于没学。

> [!note] 铁律的唯一例外：一次性的产能 / 校验 / 工具脚本
> 允许 AI 代写的**唯一例外**是「一次性的产能/校验/工具脚本」（批量生成数据、校验表格、编辑器小工具）。条件三条，缺一不可：① 必须能逐行解释；② 必须纳入"关掉 AI 重写一遍"的清单；③ 不允许生成核心玩法逻辑。其余场合仍适用上面的铁律。

**AI 在本项目里只有六种合法角色**（出题人 / 审查员 / 报错讲解员 / 文案助手 / 占位美术与音效生成 / 术语翻译官），超出这六个角色的用法都是危险信号：

| 角色 | 它擅长什么 | 它不能替代什么 |
| --- | --- | --- |
| 出题人 / 面试官 | 出判断题、逼你把概念讲清楚 | 你的实际动手练习 |
| 代码审查员 | 找边界问题、性能隐患、坏味道 | 你自己理解自己的代码 |
| 报错讲解员 | 解释报错含义、给排查步骤 | 替你做排查 |
| 文案助手 | 商店页、开发者日志、更新日志初稿 | 玩法判断、真实数据 |
| 占位美术与音效生成 | 生成 `placeholder_` 前缀的临时占位图/音效 | 正式上架资产、最终美术风格判断 |
| 术语翻译官 | 用 TS/Node 类比解释引擎概念 | 官方文档的最终解释权 |

## 1. 学习期（让 AI 出题，不让 AI 讲课）
```text
【1.1 引擎概念判断题 —— 每天一次，最划算的用法】
我是有多年 TypeScript/Node.js 经验的前端，正在学 Godot 4 + GDScript 做 2D 单机游戏。
今天学了：节点树与场景、信号（signal）、_process vs _physics_process、碰撞层与掩码、Resource。
不要给我教程，也不要解释概念。直接出 5 道场景判断题：每道给一段 GDScript 代码（带一个隐藏的错误或误区），让我判断"会不会出问题、为什么"。
一次只问一道，我答完再给下一道；我答错时先给提示，不要直接给答案。最后汇总我错的那几题是什么概念没搞懂。

【1.2 用 TS/Node 类比解释 Godot 概念】
用"前端已经熟悉的 TS/Node 概念"类比解释下面这几个 Godot 概念，每个给：
① 一句话 TS/Node 类比 ② 一句话"在 Godot 里具体指什么" ③ 一个最容易踩的坑。
概念：节点树与场景（Scene）、信号（Signal）、_process vs _physics_process、碰撞层（Collision Layer）与掩码（Mask）、Resource（自定义资源）。
要求：不要写长篇教程，每项不超过 3 行；不要编造 API，不确定的地方明确标注"以官方文档为准"。

【1.3 让 AI 当面试官（检验是否真懂）】
你是一位 Godot 游戏开发的技术面试官。我这周做的功能是（贴你的功能说明）。
请围绕这个功能连续追问我 8 个问题，难度递增：前 3 题问"是什么/怎么做"，中间 3 题问"为什么这样设计/有没有更好的方案"，最后 2 题问"如果需求变成 X，你的方案哪里会崩"。
一次问一题，我答完你只做一件事：指出我回答里不准确的那句话，然后继续下一题。

【1.4 概念自检（学完一串内容后）】
下面是我用自己的话总结的 Godot 概念笔记（贴你的笔记）。请做三件事：
① 找出其中我理解错误或含糊的地方，逐条引用我的原句；② 对每条给一个"验证方法"（我该写什么最小实验来证实/证伪）；
③ 指出我漏掉的、对这个概念很关键的一点。不要重写我的笔记。
```

## 2. Debug 期（要步骤，不要答案）
```text
【2.1 报错讲解员（标准四段式）】
【报错原文】（贴报错原文 + 完整堆栈）
【我的环境】Godot 4.x（具体小版本），Windows，GDScript，2D 项目
【我的假设】我认为原因是……（写你的猜测）
【我已经试过】1) …… 2) …… 3) ……（写你实际做过的操作和结果）
【我要什么】只给我接下来 3 步排查动作，按可能性从高到低排序，每步告诉我"执行后应该看到什么现象"。不要直接告诉我怎么改代码。

【2.2 最小复现用例】
我遇到一个问题（贴现象：什么时候发生、什么时候不发生、能不能稳定复现）。不要给我修复方案。
请给我一个"最小复现用例"的设计思路：为确认根因，我该新建一个只有一个场景的最小项目，逐步加入哪些元素、每加入一个观察什么现象、哪一步出现问题时能说明根因是什么。请给成一份 5 步以内的实验清单。

【2.3 要"为什么"而不是"改成这样"】
这段代码是我写的（贴你的代码），它的行为是（贴实际行为），我期望的是（贴期望行为）。请只回答三个问题：
① 我的代码实际执行路径是什么（按行说清楚控制流）；② 哪一行的语义和我以为的不一样，具体差在哪；
③ 为什么 Godot/GDScript 要这样设计（这样设计解决了什么问题）。不要给我改好的代码——我自己改，改完再贴给你看。

【2.4 性能问题定位】
游戏在这里会掉帧：场景是（描述场景），大约是（多少实体/多少粒子），掉帧发生在（什么操作时）。引擎是 Godot 4，机器配置是（你的配置）。
不要猜答案。请给我一份排查清单：① 该用引擎里哪些工具/面板来看真实数据；② 按"最常见的性能杀手"排序的 6 个怀疑点，每个告诉我怎么验证它是不是元凶；
③ 每一项若确认是元凶，大致的修复方向是什么（不要给代码）。
```

## 3. 代码审查期（只审查，不重写）
```text
【3.1 GDScript 性能审查】
下面是我的 GDScript 文件（贴你的代码，是项目就说明文件职责）。只做性能审查，不要重写、不要给完整实现。
重点检查：① 每帧（_process/_physics_process）里 new 对象 / 创建数组 / 字符串拼接；② 频繁 get_node / 路径查询；
③ 未释放的节点、未断开的信号连接、忘记 queue_free；④ 类型推断缺失导致的动态调用开销。
输出格式：问题所在行 → 为什么慢 → 建议方向（一句话）→ 风险等级（高/中/低）。

【3.2 状态机与信号耦合审查】
下面是我的角色状态机与相关信号连接（贴代码）。请审查架构层面的问题，不要重写：
① 状态之间是否存在隐式依赖（A 状态改了 B 状态才写的变量）；② 信号是否被用来做"跨层直接调用"而绕过了状态机；
③ 是否有节点在 queue_free 后仍被信号持有引用（悬空引用风险）；④ 如果我要加一个新的状态/事件，需要改几处？最脆弱的是哪一处？

【3.3 对象池与内存泄漏审查】
下面是我的对象池/子弹/敌人回收逻辑（贴代码）。请审查：① 对象从池里取出和归还的路径是否对称（有没有只取不还的分支）；
② 归还时是否清理了上一轮的状态（信号连接、计时器、父节点、动画）；③ 池无上限增长的风险；④ 场景切换时池里的对象会怎样。只列问题与验证方法，不要给实现。

【3.4 存档与设置代码审查（见 [[S6 系统层本地化与打包]]）】
下面是我的存档 / 设置持久化代码（贴代码）。请审查：① 哪些情况会导致读档崩溃或存档损坏；② 是否有设置项忘记落盘；
③ 路径是否用了 res:// 或绝对路径（应该是 user://）；④ 版本迁移缺失的分支。每条给出"怎么手动复现"。
```

## 4. 设计期（AI 只能给假设，不能替玩家做判断）
```text
【4.1 唱反调的策划】
下面是我的一句话玩法陈述（贴你的陈述）。你现在是一个毒舌但专业、只想把项目做死的游戏策划。请做三件事，不要夸我：
① 指出这个陈述里最空洞、最像"套模板"的一句，并说明玩家为什么不会被吸引；② 列出 5 个"这个玩法在 30 分钟后就腻了"的具体场景；
③ 针对最致命的 2 个问题，各给出 2 个能在一周内实现的小改动方向。最后明确告诉我：这些都是假设，必须靠真人试玩验证。

【4.2 竞品拆解维度清单】
我要拆解竞品（贴游戏名或品类）。请给我一份拆解维度清单，用于我自己看实机视频/试玩并填表：
至少覆盖 ①前 30 秒钩子 ②核心动词与反馈 ③失败与重试代价 ④内容量与重复度 ⑤成长/解锁曲线 ⑥UI 信息密度 ⑦音效与 Juice ⑧价格与体量 ⑨差评集中点。
每个维度给出"我该具体记录什么"的一句话说明，并留出填写栏。不要替我评价这些游戏。

【4.3 把 30 秒爽感拆成实现清单】
我描述一遍玩家开局 30 秒会经历什么（贴你的描述）。请把它拆成"可实现的反馈清单"：
逐个动作列出可能叠加的反馈手段（动画、粒子、屏震、音效、顿帧、数值飘字、镜头缩放、颜色变化），
每条标注：实现成本（低/中/高）、是否必须、以及它服务的是"力量感/速度感/命中感"中的哪一种。提醒我：这只是实现手段清单，爽不爽必须靠真人试玩判断。

【4.4 玩法裁剪仲裁】
我想加一个新功能：（贴功能描述）。请扮演"只想让项目按时上线的制作人"，用这三个问题审我：
① 它是否改变了玩家每 30 秒要做的决定？② 删掉它核心循环还成立吗？③ 能在一周内做出可玩版本吗？
然后给出你的判断（保留 / 削弱版 / 进 Cut 列表），并说明如果我坚持要做，应该砍掉现有哪一部分来腾时间。
```

> [!tip] 第 4 组的使用纪律
> 竞品拆解表、垂直切片与陌生人试玩的流程见 [[S3 垂直切片与竞品拆解]]；该不该砍功能见 [[附录 C 范围与功能裁剪决策卡]]。**AI 给的玩法意见一律当"待验证假设"，不要当结论。**

## 5. 文案与商店页（不许夸张、不许虚假承诺）

> [!warning] 硬约束
> 商店页文案属于**对外承诺**。夸大的功能描述、未实现的特性宣传、虚假的"XX 万玩家"都是平台违规与退款/差评来源。AI 生成的文案**必须逐句核对是否与游戏实际内容一致**，见 [[S7 Steam 上架全流程]]。
```text
【5.1 商店页短描述 A/B 版本】
这是我的游戏：一句话玩法陈述（贴）+ 核心机制（贴）+ 参考同类游戏（贴）。
请写两版 Steam 商店页短描述，各不超过 **300 字符（约 45–50 个英文单词，Steam 短描述上限 300 字符）**：A 版主打"机制独特"，B 版主打"情绪/氛围"。
硬性要求：只描述游戏里真实存在的东西，不许出现 "revolutionary""best ever""millions of players" 这类词，
不许承诺更新频率、联机、后续内容。每写一句，在括号里标注它对应我给的哪个事实。

【5.2 提炼 3 个卖点】
基于上面的游戏描述（贴），帮我提炼 3 个卖点，并给每个卖点：① 玩家能一眼看懂的一句话；
② 支撑它的具体游戏内容（必须来自我给的描述，不要发明）；③ 它是否适合出现在预告片前 10 秒。
如果一个卖点找不到实际内容支撑，明确说"这一条撑不起来"。

【5.3 开发者日志草稿】
我要写一篇开发者日志，主题是（贴主题，例如"我把存档系统重做了一遍"）。事实素材：（贴你实际做了什么、踩了什么坑、花了多久）。
请写一篇 400 字左右的草稿，风格：诚实、具体、不吹。必须包含：一个具体的坑、一个具体的数字、一句我对玩家的真实想法。
不许出现励志鸡汤和"感谢大家支持"式结尾（除非我真的提供了相关事实）。

【5.4 更新日志（Patch Notes）】
这是本次更新实际改动的内容（贴你的改动列表，含 Bug 修复）。请整理成 Steam 更新日志格式，分 Added / Changed / Fixed 三节，条目简短、动词开头。
硬性要求：① 只写我给的改动，不许补充任何我没写的功能或"性能提升 X%"；② 未修复的问题如我提供了，放在 Known Issues 一节；
③ 不要为修过的 Bug 道歉过度，也不要暗示未来内容。
```

## 6. 产能与管线（把重复劳动交出去）
```text
【6.1 批量生成关卡数据】
我需要批量生成关卡配置文件。格式如下（贴一个手写的示例文件）。规则：（贴你的规则，例如每关敌人数随关卡序号增长、Boss 关在第 10 的倍数）。
请写一个 Godot 里可用的 GDScript 编辑器脚本（EditorScript）或一个独立 Python 脚本，读取规则表生成数据文件，要求：
① 有随机种子参数，同样种子结果可复现；② 生成后打印每关的数值摘要供我肉眼检查；③ 数值上下限越界时报错而不是静默生成。只给脚本和简短用法说明，不要给教程。

【6.2 数值表格校验脚本】
这是我的数值表结构（贴 CSV 表头 + 几行示例数据）与设计约束（贴约束，例如攻击力 > 0、稀有度单调递增）。请写一个校验脚本，检查：
① 类型/范围错误 ② 主键重复 ③ 引用了不存在的 ID ④ 违反设计约束的行。
输出：每条错误给出"文件 + 行号 + 原因"，全部通过时退出码 0，有错时非 0。不要顺手帮我"修复"数据。

【6.3 编辑器工具脚本】
我每天都要手动做这件事：（贴你的重复操作，例如"把选中的 Sprite2D 批量设置过滤模式和居中对齐"）。
请写一个 Godot 4 的 EditorScript / 编辑器插件，让我在编辑器里一键完成。要求：
① 对选中的多个节点生效 ② 只修改必要的属性，不碰其他 ③ 没有选中节点时给出明确提示而不是报错。给代码 + 如何在编辑器里运行的说明。

【6.4 自动化收尾检查】
这是我的发布前自检清单（贴清单，验收标准参考 [[S6 系统层本地化与打包]]）。请帮我把它变成一份可执行的检查脚本或结构化清单模板：
能自动检查的（例如文件是否存在、版本号是否一致、资源是否缺失）标为"可自动化"并说明用什么检查，必须人工操作的标为"人工"。不要替我执行任何检查。
```

> [!tip] 把重复劳动交出去的前提
> 脚本是产能工具，不是玩法判断。写完必须**自己核对一次输出**：批量生成的关卡数据要肉眼抽查，校验脚本要能对故意写错的一行报错。管线全流程见 [[S4 资产管线与美术音频]] 与 [[S5 内容量产与打磨]]。

## 7. 防幻觉三步验证（问完 AI 必须做）

> [!important] AI 会一本正经地编造引擎 API、配置项名、命令行参数。
> 这不是它"坏了"，而是它的工作原理。**任何你打算写进项目的 API，都必须过这三步。**

```text
第一步：查官方文档
  → 去 Godot 官方文档搜这个类/方法/属性名。搜不到 = 大概率是编的。
  → 注意版本：Godot 3 与 4 的 API 差别很大，网上教程大量是 3.x 的。
第二步：写 10 行最小复现
  → 新建一个空场景，只放这段代码 + 一个 print，跑一次。
  → 能跑通 → 至少 API 存在；行为和你以为的一致 → 才敢用进项目。
  → 报错或行为不符 → 把报错贴回去问 AI（不要问"帮我改"，问"为什么"）。
第三步：用自己的话反向解释
  → 合上文档和对话，用一句话写下"这个 API 做什么、参数是什么、返回什么、什么情况下不该用"。
  → 写不出来，说明你只是抄了代码，等于没学。
```

把这个模板直接发给 AI 让它配合你做第三步：
```text
我准备在项目里使用这个 Godot API / 配置项：（贴名称与你从 AI 或网上看到的用法）。请做三件事：
① 明确告诉我你有多确定它存在、属于哪个版本，不确定就直说"不确定，以官方文档为准"；
② 给一个 10 行以内的最小验证片段，让我能立刻确认它是否有效；③ 列出 3 种"我误用它会出现的典型现象"，方便我在测试里识别。
```

## 8. 禁止清单

> [!warning] 这五件事不要做
> **1. 不要让 AI 生成整个游戏。** 你得到的是一堆你读不懂、改不动、无法调试的代码。项目的所有权和可维护性都在你手里——AI 写的东西你必须能重写一遍，否则不许进仓库。
> **2. 不要不分析就把报错丢给 AI。** 一句"这段报错怎么修"换来的是碰运气式修改。必须先写你的假设 + 已试过的方案（见第 2 组），否则你会养成"看不懂也能继续"的习惯，而发售前你一定会为此付出代价。
> **3. 不要相信 AI 编造的引擎 API / 配置项 / 命令行参数。** 一切都要过第 7 组的防幻觉三步验证。**不确定就写"以官方文档为准"**，永远不要凭 AI 的说法就觉得某个选项存在。
> **4. 不要用 AI 生成版权不明的正式上架资产而不看平台披露要求。** 商店素材、宣传图、游戏内美术、配音、音乐——正式上架前必须确认授权来源与 AI 内容申报要求，见 [[S7 Steam 上架全流程]] 与 [[S4 资产管线与美术音频]]。占位素材和上架素材是两回事。
> **5. 不要让 AI 替你做"好不好玩"的判断。** 玩法、手感、数值体感、难度曲线只能靠真人试玩，AI 的输出永远是**假设**。把它的意见当"待验证的假设"，而不是结论。

> [!tip] 一句话记住整套用法
> **AI 帮你缩小搜索空间，不帮你承担判断责任。** 出题、审查、讲报错、写文案初稿、批量脚本——这些都能交出去；**动手、判断、重写、拍板**只能你自己来。
