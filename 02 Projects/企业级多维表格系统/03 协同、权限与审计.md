# 03 协同、权限与审计（企业级的分水岭）

> 这三个能力决定系统是「团队能用的工具」还是「一个人玩的 Demo」。也是工作量最容易被低估的部分——协同、权限、审计加起来通常占总工时的 40%。
>
> 结论先行：
> 1. **不要一上来做 OT/CRDT**。单元格级的「操作日志 + 乐观锁 + 服务端权威广播」能覆盖 95% 的企业内场景，成本只有 OT 的 1/5。
> 2. **权限以应用层查询改写为主，Postgres RLS 只做兜底**。RLS 有 owner 绕过、连接池串会话这些坑，靠它单打独斗必然出现「配置正确但实际越权」。
> 3. **变更日志（change_log）一份数据，四家用**：协同广播、断线重放、单元格历史、审计取证。所以它的表结构要一次设计对。

---

## 1. 协同到底要解决什么

| 问题 | 是否必须（P0） | 方案 |
|---|---|---|
| A 改了一个单元格，B 的界面要看到 | ✅ 必须 | 服务端广播变更（WebSocket） |
| 同一个人手快连点两下，不能出现脏写 | ✅ 必须 | 乐观锁 `version` + 幂等 `opId` |
| 两人同时改同一格，结果要可解释 | ✅ 必须 | 服务端权威 + 冲突提示 |
| B 断线了，回来能看到中间错过的改动 | ✅ 必须 | `seq` 增量拉取 |
| 谁在编辑哪一格（在线状态） | 👍 加分 | presence + 临时锁提示 |
| 两人同时编辑同一段富文本，字符级合并 | ❌ P2 | Yjs（前端）+ 后端只存储转发 |
| 撤销/重做跨人协作 | 👍 加分 | 基于 op 的反向操作 |

如果只做前四条，就是「企业内够用」的协同；把 CRDT 塞进主线，团队会在一致性测试里耗掉两个月。

## 2. 三种协同路线的真实成本

| 路线 | 实现 | 一致性 | 代价 | 建议 |
|---|---|---|---|---|
| **A. 轮询刷新** | 前端每 5~10 s 拉一次 | 最终一致，冲突靠后端 | 体验差、请求放大 | 只做兜底 |
| **B. 单元格操作日志 + 乐观锁 + 广播** | 一个表一个 `change_log`，服务端串行/原子写，WebSocket 广播 | 服务端权威，单格 LWW | 需要 op 幂等、重放、冲突 UI | **P0 选它** |
| **C. changeset / OT（APITable 路线）** | 独立房间服务持有内存快照，按 revision 应用 operation | 强一致、可回放 | 房间服务、快照压实、运维成本 | P1 视需求 |
| **D. CRDT（Yjs）** | 前端 Yjs，后端存二进制更新 | 自动合并，离线友好 | **Java 没有官方 y-crdt 绑定**（只有 Rust/WASM/C 和社区 Kotlin 绑定）；服务端无法校验/查询文档内部 | 只用于富文本字段，P2 |

> 事实依据：y-crdt 官方仓库只列 Rust/C/WASM 与 Python/Ruby/.NET/Swift/Kotlin 绑定，查不到 Java；见 [`_research/企业级多维表格系统/02-java后端-事实核查.md`](../../_research/企业级多维表格系统/02-java后端-事实核查.md) §6.1。

**B 的关键设计**：服务端不做"整行覆盖"，而是**每格一个操作**，用 `jsonb_set` 原子写，天然避免"读-改-写"丢更新：

```sql
update record
   set data    = jsonb_set(data, '{f_1001}', to_jsonb('新值'::text), true),
       version = version + 1,
       updated_at = now()
 where datasheet_id = 42 and id = 9001
 returning version;
```

同一行不同字段并发时，PG 行锁会让它们排队（毫秒级）；`version` 只用来让客户端知道"我基于哪一版"。

## 3. 变更日志（change_log）：一张表解决四件事

```sql
create table change_log (
  datasheet_id bigint      not null,
  seq          bigint      not null,        -- 每张数据表内单调递增
  op_id        uuid        not null,        -- 客户端生成，幂等键
  record_id    bigint,
  field_id     bigint,
  op_type      text        not null,        -- record_add/record_delete/cell_set/field_add/view_update/link_add...
  before_value jsonb,
  after_value  jsonb,
  actor_id     bigint      not null,
  client_id    text,                        -- 区分多标签页/多端
  created_at   timestamptz not null default now(),
  primary key (datasheet_id, seq)
);
create unique index uk_change_op on change_log (op_id);   -- 重复投递直接返回已有结果
create index idx_change_record on change_log (datasheet_id, record_id, seq desc);
```

用途：

| 用途 | 怎么用 |
|---|---|
| 协同广播 | 写入成功后把 `{seq, op_type, record_id, field_id, after_value}` 推到房间 |
| 断线重放 | 客户端带 `lastSeq` 重连 → `GET /datasheets/{id}/changes?sinceSeq=` |
| 单元格历史 | `where record_id=? and field_id=? order by seq desc`，做"查看历史/回滚这一格" |
| 审计取证 | 谁在什么时候把哪个值改成什么；导出为审计报表 |

设计要点：

1. **seq 的来源**：同一数据表内必须单调。用 `pg_advisory_xact_lock` 或"每表一行计数器表 `update ... returning`"取号，不要用全局序列（跨表乱序但没关系，跨表本来就不需要顺序）。Redis `INCR` 也可以，但重启/丢数据会回退，**别用它做唯一依据**。
2. **幂等**：客户端重试、网关重放都可能重复投递。`op_id` 唯一索引 + 插入冲突时返回之前的 seq，重复操作天然安全。
3. **保留期**：热表保留 7 天（或 1000 万条），之后归档到对象存储；`audit_log` 单独保留 6 个月以上，不参与清理。
4. **快照压实**：change_log 是增量，新建的客户端只需要"当前页 + sinceSeq"。如果客户端 `lastSeq` 太旧（< 最小保留 seq），直接重拉页面数据，别做全量重放。
5. **写入量**：一次单元格编辑一条，一次批量粘贴 N 条。批量操作合并成一个 `batch` 类型的 op，`after_value` 里放数组，避免日志被粘贴操作打爆。

### 版本历史（用户能看见的"历史记录"）

- **单元格级**：直接查 `change_log`。
- **整行级**：`record_revision` 表每 10 分钟或每 20 次变更存一个快照；用户看到的是"时间轴上的行快照"。
- **回滚**：不要物理回写旧值，而是**生成反向 op 走正常写入链路** —— 这样广播、审计、协同都自动生效。

## 4. 冲突策略：按字段类型决定，不是一刀切

| 字段类型 | 并发写策略 | 用户看到什么 |
|---|---|---|
| 文本、数字、日期 | 服务端 LWW（`version` CAS，失败返回 409 + 最新值） | "该单元格已被张三修改为 X，保留我的 / 用最新" |
| 多选、成员、关联 | 存**集合增删操作**（`add` / `remove`），不是覆盖 | 两人各加一个标签 → 两个都在（这才是对的） |
| 复选框 / 开关 | LWW | 最后一次点击生效，可提示 |
| 附件 | 追加式（上传即追加，删除单独 op） | 两人各传一个 → 两个都在 |
| 富文本 | 字符级合并（Yjs）或 LWW | P2 再谈 |
| 公式 / 查找 / 汇总 | 客户端只读，服务端算 | 不产生冲突 |

`409` 响应的标准结构，直接决定前端能不能写出好用的冲突 UI：

```json
{
  "code": "CELL_CONFLICT",
  "recordId": "9001",
  "fieldId": "f_1001",
  "yourValue": "A",
  "currentValue": "B",
  "currentVersion": 12,
  "changedBy": {"id": "1001", "name": "张三"},
  "changedAt": "2026-11-16T12:00:00+08:00"
}
```

## 5. 断线、离线与多端

```
客户端                          服务端
  │  ws connect(token)            │
  │ ────────────────────────────▶ │ 鉴权：token → userId → 可见表列表
  │ ◀──── subscribed {lastSeq}    │
  │                               │
  │ 断网 30s，期间产生 3 条本地编辑  │
  │ ── POST /ops/batch (opIds) ──▶ │ 逐条幂等执行，返回每条 seq/结果
  │ ◀──── {results:[ok, conflict] }│
  │                               │
  │ ◀──── changes since lastSeq   │ 补齐断线期间别人的改动
```

- **本地待提交队列**必须持久化（IndexedDB），刷新页面不丢。
- 离线期间产生的编辑用 `opId` 去重，恢复后按顺序重放；冲突的逐条弹。
- 多标签页：用 `BroadcastChannel` 同步本地状态，避免同一浏览器两个页面互相覆盖。

## 6. 实时通道：Java 侧怎么搭

| 组件 | 选择 | 说明 |
|---|---|---|
| 协议 | **Spring WebSocket + STOMP** | 与 Spring Security 集成最顺；`/topic/datasheet/{id}` 订阅模型 |
| 备选 | Netty 自研协议 / RSocket | 连接量大、要精细控制时；成本高 |
| 多实例广播 | Redis Pub/Sub（`RedisMessageListenerContainer`）或 Redisson `RTopic` | **Pub/Sub 不持久**，丢消息靠"快照 + sinceSeq 补齐" |
| 大房间 | Kafka / Redis Streams | 需要积压与回放时；一般企业内用不到 |

关键参数与坑：

- **订阅鉴权**：`SUBSCRIBE` 前校验用户对该表的读权限，否则等于开了个数据后门。
- **心跳**：25 s 内无消息发 ping，60 s 无响应断开。
- **消息大小**：单条 op 限 32 KB（附件只传 token），超限拒绝。
- **限流**：每连接 20 msg/s，超出断开并提示（防脚本刷）。
- **背压**：慢客户端不要丢变更，用 100 ms 窗口合并成 batch 下发。
- **连接规模**：单实例保守估 5k~10k 长连接；1 万人在线 → 2~4 个 WS 实例 + 粘性会话（或让所有实例都能处理）。

```java
// 骨架：订阅 + 鉴权 + 广播（Spring WebSocket / STOMP）
@Configuration
@EnableWebSocketMessageBroker
class WsConfig implements WebSocketMessageBrokerConfigurer {
  @Override public void registerStompEndpoints(StompEndpointRegistry r) {
    r.addEndpoint("/ws").setAllowedOriginPatterns("https://*.corp.example.com")
     .addInterceptors(new AuthHandshakeInterceptor());   // 握手时验 token
  }
  @Override public void configureMessageBroker(MessageBrokerRegistry r) {
    r.enableSimpleBroker("/topic");                        // 多实例时换成 Redis 中继
    r.setApplicationDestinationPrefixes("/app");
  }
}
```

## 7. 权限模型

### 7.1 主体与资源

```
主体：用户 user / 部门组 group / 角色 role(space owner/admin/editor/commenter/viewer) / 匿名 token
资源：空间 space → 文件夹 folder → 数据表 datasheet → 视图 view → 字段 field → 记录 record
动作：read / create / update / delete / share / manage
```

### 7.2 授权表

```sql
create table permission (
  id            bigint primary key,
  space_id      bigint not null,
  resource_type text   not null,      -- space/folder/datasheet/view
  resource_id   bigint not null,
  subject_type  text   not null,      -- user/group/role/everyone
  subject_id    bigint,
  actions       text[] not null,      -- {read,write,delete,share,manage}
  row_filter    jsonb,                -- 行级权限，复用筛选 DSL（01 文档 §6.1）
  field_deny    bigint[],             -- 字段级：禁读/禁写字段 id
  created_at    timestamptz not null default now()
);
create index idx_perm_res on permission (resource_type, resource_id);
```

行级权限的配置就是一串筛选条件，例如"部门 = 当前用户部门 AND 状态 ≠ 已归档"，编译后追加到查询 `WHERE`：

```sql
-- 权限注入后的查询（注意：和数据筛选同层编译，不要字符串拼）
select r.* from record r
where r.datasheet_id = 42
  and r.deleted_at is null
  and (r.data->>'f_dept' = '研发部' or r.data->>'f_owner' = '1001')   -- row_filter
  and <用户筛选条件>
order by r.rank, r.id
limit 201;
```

### 7.3 字段级权限必须在服务端做响应裁剪

只在前端隐藏列 = 没做权限。响应 DTO 组装时按 `field_deny` 剔除字段，写操作时校验字段是否可写。**导出接口同样要裁剪** —— 这是最常见的数据泄露路径。

### 7.4 权限计算的优先级

```
effective = ∪(所有人权限, 用户所在组权限, 用户直接权限, 分享链接权限) − 字段拒绝
          ∩ 上级资源权限（空间禁读 → 表一律不可读）
```

缓存：`Caffeine<userId+resourceId, EffectivePermission>`，TTL 60 s；任何权限变更通过 Redis 频道广播失效（多实例）。

### 7.5 分享与 API

| 形态 | 表 | 要点 |
|---|---|---|
| 分享链接 | `share_token(token, resource_type, resource_id, permission, password_hash, expires_at, created_by)` | 只读/可编辑可选；密码 + 过期；访问日志 |
| 嵌入（iframe） | 同上 + `embed=true` | 限制父页面域名（CSP frame-ancestors） |
| 开放 API | `api_token(token_hash, space_id, scope jsonb, expires_at)` | 按表限权、限流、可轮换；**只存 hash** |
| 自动化/机器人 | 系统内置角色 | 权限独立配置，审计里标注为"自动化" |

### 7.6 Postgres RLS 只做兜底（如果你想用）

- 表 owner 默认绕过 RLS，必须 `ALTER TABLE record FORCE ROW LEVEL SECURITY`；
- 超级用户和 `BYPASSRLS` 角色永远绕过；
- 连接池（HikariCP / PgBouncer）下必须每事务 `SET LOCAL app.user_id = ...`，并保证归还连接时清理；
- 策略表达式性能要实测，别让每行都跑一次复杂子查询。

> 官方依据：[Row Security Policies (PG 18)](https://www.postgresql.org/docs/18/ddl-rowsecurity.html)。

## 8. 审计

审计和变更日志**分开建表**：一个给协同用（会被清理），一个给合规用（只增不删、独立保留）。

```sql
create table audit_log (
  id           bigint generated always as identity,
  space_id     bigint not null,
  actor_id     bigint,
  actor_name   text,
  action       text not null,       -- login / permission_change / export / delete / api_call / share_access
  resource_type text,
  resource_id  bigint,
  detail       jsonb,               -- 变更前后、导出条数、IP、UA
  ip           inet,
  user_agent   text,
  created_at   timestamptz not null default now()
) partition by range (created_at);   -- 按月分区，便于归档
```

必须记录的事件（企业内审计的常规要求）：
- 登录/登出/失败登录、SSO 绑定
- 权限授予/回收、分享链接创建与访问、API token 创建
- 数据导出（CSV/XLSX/API 全量拉取）——**导出是最需要留痕的动作**
- 数据删除（软删、回收站清空）、表结构变更
- 自动化规则执行、Webhook 投递结果

保留与合规：审计日志 ≥ 6 个月（等保 2.0 三级常见的硬要求），写入用异步队列 + 只追加表，**不允许 UPDATE/DELETE 权限给应用账号**。

## 9. 一张图看全链路

```
编辑请求
  → 鉴权（表级/字段级）
  → 校验（类型/选项/关联记录存在性/唯一性）
  → 事务：jsonb_set 更新 record + 写 change_log + 写 audit_log（异步）
  → 成功后：Redis Pub/Sub → 各实例 → STOMP 广播给房间内其他客户端
  → 失败：409 带当前值 / 403 带原因
```

## 10. 验收清单

- [ ] 两人同时改同一格：一人成功，另一人收到 409 + 最新值，界面可一键采用
- [ ] 两人同时给同一条记录加不同标签：两条都保留（集合语义）
- [ ] 断网 1 分钟内的编辑：恢复后全部落库，无重复（改 20 次只产生 20 条 change_log）
- [ ] 客户端带旧 `sinceSeq` 重连：能拉到全部增量；`sinceSeq` 早于保留期的：自动整页刷新
- [ ] 越权测试：无权限用户直接构造 `GET /records`、导出接口、WebSocket 订阅，三处都 403
- [ ] 字段级权限：被禁字段不出现在任何响应体（含导出、API、Webhook）
- [ ] 权限变更 60 s 内全实例生效（含已登录用户）
- [ ] 审计查询：能按人/时间/资源查出"谁导出过这张表"
- [ ] 1000 人同时在线、单表 200 人编辑：WS 不崩、无明显延迟堆积
