# 企业级多维表格系统 · 从零搭建总体方案

> 目标：在企业内网私有化部署一套「类 Airtable / 飞书多维表格」系统 —— 前端用开源 **VTable** 渲染，后端用 **Java** 实现，支撑几十张业务表、百万行数据、全员协作与行/列级权限。
>
> 阅读顺序：**本文**（全局判断与选型）→ [01 数据模型与存储引擎](01%20数据模型与存储引擎.md) → [02 VTable 前端落地](02%20VTable%20前端落地.md) → [03 协同、权限与审计](03%20协同、权限与审计.md) → [04 从零落地路线](04%20从零落地路线.md)。
>
> 事实底稿（带官方链接）：[VTable 核查](../../_research/企业级多维表格系统/01-vtable-事实核查.md)、[Java 后端核查](../../_research/企业级多维表格系统/02-java后端-事实核查.md)。结论基于 2026-11-16 的官方文档与包版本。

## 0. 五个结论，先看这里

1. **VTable 只占工作量的 20%（经验值）**。它是 Canvas 渲染引擎，没有数据层、没有服务端分页协议、筛选 UI 和导出都在插件里。剩下 80% 是后端的元数据模型、查询编译、权限、协同、导入导出。
2. **"从零"的正确姿势不是先搭架子，而是先做一个垂直切片**：建表 → 加字段 → 录 3 条 → 列表渲染 → 编辑提交 → 刷新还在。这一条链路走通，后面都是它的复制品。
3. **存储用「元数据强类型 + 记录 JSONB」**，动态字段不做 DDL；千万行级再叠加值列存。详见 01。
4. **协同用「单元格操作 + 乐观锁 + 变更日志广播」，不要上手 OT/CRDT**。y-crdt 官方只出 Rust/C/WASM 绑定，社区绑定里没有 Java（只有 Kotlin 等），自研 OT 是 2~4 人月的坑。详见 03。
5. **权限默认在应用层做查询改写**，Postgres RLS 只做兜底（owner 绕过、连接池串会话这两个坑足以让权限形同虚设）。

## 1. 什么才算「企业级多维表格」

先对齐能力清单，避免做到一半发现少了一块：

| 能力域 | 必须（P0） | 应该（P1） | 可以（P2） |
|---|---|---|---|
| 表结构 | 建表、加字段、字段类型 ≥ 10 种、改选项、字段隐藏 | 字段类型扩展（评分/进度/自动编号/公式） | 自定义字段类型/插件 |
| 数据 | 增删改查、批量编辑、附件、软删除回收站 | 关联表、查找、汇总、唯一性校验 | 双向关联、无限跨表链接 |
| 视图 | 网格视图、筛选、排序、分组、列宽冻结 | 看板、日历、甘特、表单 | 画廊、地图、仪表盘 |
| 计算 | 基础公式（算术/文本/日期） | 汇总/查找/跨表引用、依赖重算 | 自定义函数、脚本 |
| 协作 | 多人实时刷新、冲突提示、在线状态 | 单元格历史、行历史、评论 @ | 字符级协同、协同光标 |
| 权限 | 空间/表级角色、只读分享链接 | 行级权限、字段级权限、API token | 审批流、动态权限 |
| 导入导出 | CSV/XLSX 导入导出、错误行报告 | 百万行后台导出、定时导出 | 数据同步到外部库 |
| 企业能力 | 审计日志、单点登录（OIDC/LDAP）、备份 | 多租户、水印、操作回放 | 私有化离线包、等保合规包 |

> 与 SaaS 版的差异：企业内部更看重**数据不出内网、SSO、审计、与现有系统集成（API/Webhook）**，而对"漂亮的模板市场"需求低。选型时应把预算压在前者。

## 2. VTable 的边界（决定架构怎么切）

| VTable 1.26.8 提供 | 你必须自己写 |
|---|---|
| Canvas 渲染、虚拟滚动（官方称百万级数据） | 数据从哪来、怎么分页 |
| 列定义、表头分组、冻结、合并、主题、tooltip、右键菜单 | 菜单里的业务动作 |
| 4 个内置编辑器 + `IEditor` 自定义 | 选项/成员/附件/关联的编辑器 |
| `customLayout` / `customRender` 自定义单元格 | 每种字段类型的渲染函数 |
| 排序图标与事件（**前端排序**） | 后端排序 + 状态回传 |
| 插件：`FilterPlugin`（前端筛选）、`TableExportPlugin`（默认导当前页）、`HistoryPlugin` | 服务端筛选 DSL、大数据导出、操作幂等 |
| — | 元数据模型、权限、协同、审计、公式 |

结论：架构上必须有一层**自己的数据层**（`RecordStore` + 编辑队列 + 实时客户端），VTable 只当"渲染器"。详见 [02](02%20VTable%20前端落地.md)。

## 3. 总体架构

```
┌───────────────────────────── 浏览器 ─────────────────────────────┐
│ React 18/19 + TS                                                  │
│  ├─ 视图壳：工具栏 / 筛选面板 / 字段配置 / 行详情 / 评论           │
│  ├─ DataSheetTable：columns = f(元数据), records = f(数据层)       │
│  └─ 数据层：RecordStore / EditQueue / RealtimeClient(WS)          │
└───────────────┬──────────────────────────────────────────────────┘
                │ HTTPS(REST) + WSS                 
┌───────────────▼──────────────────────────────────────────────────┐
│ 接入层：Nginx / Ingress（TLS、限流、静态资源）                      │
├──────────────────────────────────────────────────────────────────┤
│ Java 应用层（Spring Boot 4.1.x，无状态，可水平扩）                  │
│  ├─ 元数据服务：space / datasheet / field / view                   │
│  ├─ 记录服务：CRUD、批量、附件、导入导出                            │
│  ├─ 查询服务：筛选 DSL → AST → SQL（jOOQ）、游标分页               │
│  ├─ 公式服务：解析/依赖图/增量重算（异步）                          │
│  ├─ 协同服务：WebSocket + change_log + presence + 广播             │
│  ├─ 权限服务：权限计算 + 查询改写注入（所有入口共用）                │
│  └─ 平台服务：SSO、审计、Webhook、OpenAPI、定时任务                 │
├──────────────────────────────────────────────────────────────────┤
│ 存储层                                                            │
│  ├─ PostgreSQL 18（元数据 + 记录 JSONB + change_log + 审计）        │
│  ├─ Redis 8（会话、权限缓存、presence、Pub/Sub 广播）               │
│  ├─ S3/MinIO（附件、导出文件、快照）                                │
│  └─ （可选）OpenSearch / ClickHouse：全文检索与 BI 大表             │
└──────────────────────────────────────────────────────────────────┘
```

为什么 Java 单体起步、按模块切：多维表格的核心难点在**查询编译与数据一致性**，这两块在单体内最容易保证事务边界；协同/公式/导出可以独立部署（同一份代码，不同 profile），等真到瓶颈再拆服务。

## 4. 技术栈选型（2026-11 核实版本）

| 层 | 选择 | 版本 | 理由 / 替代 |
|---|---|---|---|
| 运行时 | Java（LTS） | **25** | 25 是当前 LTS（下一个 29 / 2027-09）；虚拟线程适合大量 IO 等待的导出/协同场景 |
| 框架 | Spring Boot | **4.1.2** | 兼容 Java 17~27；4.2 尚未 GA，不进生产基线 |
| Web | Spring MVC + Spring WebSocket(STOMP) | 7.0.10 / Security 7.1.2 | 协同早期用 STOMP 最省事；连接量上万再考虑 Netty |
| 数据库 | PostgreSQL | **18.7** | JSONB + GIN + 表达式索引 + STORED 生成列；19 仍是 RC，不用 |
| 连接池 | HikariCP | 7.0.2（BOM） | 默认够用 |
| 查询层 | **jOOQ 3.21.9** + 自研 DSL→AST→SQL | | 动态表/动态字段下类型安全有限，但 SQL 表达力最强；MyBatis 也可，别用 JPA Specification 做核心查询 |
| 迁移 | Flyway | 12.4.0（需 `flyway-database-postgresql`） | 元数据表结构演进 |
| 缓存/协同 | Redis + Lettuce | 8.10.3 | 权限缓存、presence、Pub/Sub |
| 附件 | MinIO / S3（预签名直传） | — | 文件不经过应用服务器 |
| Excel | **FastExcel**（EasyExcel 后继）或 POI SXSSF | 1.3.0 / POI 6.0.0 | 流式读写；百万行导入走 `COPY` |
| 公式 | 自研 Pratt 解析 + AST 求值 | — | Aviator 可做求值后端；Calcite 不适合编译筛选 DSL |
| 可观测 | Micrometer + OTel（BOM 1.17.2 / 1.62.0）+ Prometheus + Grafana | | Actuator 起步 |
| 前端 | React 18/19 + TS + Vite | | VTable 官方 React 封装 |

> 版本来源与逐条链接见 [Java 后端核查](../../_research/企业级多维表格系统/02-java后端-事实核查.md) §2。选版本的原则：**用最新 LTS + 最新 GA，但只选一个 patch 线，别混用 RC**。

## 5. 后端模块划分（Maven 多模块）

```
mdt-backend/
├── mdt-common        错误码、DTO、Jackson/JSONB 序列化、雪花 ID、分页游标
├── mdt-metadata      space/datasheet/field/view 领域与仓储
├── mdt-query         筛选 DSL、AST、SQL 编译器、游标分页、聚合
├── mdt-record        记录读写、批量、软删、值列存双写（可选）
├── mdt-formula       公式解析、依赖图、增量重算
├── mdt-permission    权限计算、策略缓存、查询改写注入（依赖 mdt-query）
├── mdt-collab        WebSocket、change_log、presence、广播、重放
├── mdt-import-export CSV/XLSX 流式导入导出、PG COPY
├── mdt-platform      SSO、审计、Webhook、OpenAPI、定时任务
├── mdt-bootstrap     Spring Boot 启动、配置、Actuator
└── mdt-contract      OpenAPI 契约与前端类型生成
```

依赖方向单向：`common ← metadata/query/record ← formula/collab/permission ← bootstrap`。**`mdt-query` 不允许依赖 `mdt-permission`**——权限通过"编译期回调/上下文"注入条件，避免循环依赖，也保证所有查询都能被权限层拦住（漏一层就是越权）。

## 6. 数据模型总览

```
space ─┬─ datasheet ─┬─ field（类型/选项/公式/关联配置）
       │             ├─ view（筛选/排序/分组/列宽/冻结）
       │             └─ record（data JSONB + version + rank + deleted_at）
       ├─ permission（资源 × 主体 × 动作 + 行过滤 + 字段拒绝）
       ├─ member / group
       └─ share_token / api_token

横切：change_log（协同+历史）、audit_log（合规）、attachment、comment、automation、webhook
```

完整 DDL、字段类型 ↔ JSONB 编码、查询编译、分页与索引策略见 [01 数据模型与存储引擎](01%20数据模型与存储引擎.md)。

三条不可妥协的约定：
1. **元数据只存 id**：选项、成员、关联记录都存 id，显示名在读取时翻译。改名字不用回填数据。
2. **空值 = 不存在**，不写 `{"f": null}`。
3. **所有查询走同一个编译器**，包括导出、Webhook、看板统计——否则权限和筛选总有一处漏。

## 7. 六条核心链路

| 链路 | 关键点 | 详见 |
|---|---|---|
| 列表查询 | 视图配置 + 权限过滤 → DSL → SQL → keyset 分页 → 返回 `{columns, records, nextCursor}` | 01 §6~7 |
| 单元格编辑 | 乐观更新 → `PATCH`（opId + baseVersion）→ `jsonb_set` 原子写 → 广播 → 失败回滚/冲突 UI | 02 §6、03 §2 |
| 批量粘贴 | 一次请求多个 op，服务端按批事务；日志合并成一条 batch op | 03 §3 |
| 公式重算 | 变更 → 依赖图找受影响记录 → 异步批量重算 → 广播结果 | 01 §10、03 |
| 导入 | 流式解析 → 字段映射预览 → 批量 `COPY`/`INSERT` → 错误行报告 → 进度查询 | 01 §12 |
| 导出 | 只读副本 + `COPY TO STDOUT` 流式响应；XLSX 走 SXSSF；超 50 万行提示 CSV | 01 §12 |

## 8. 关键设计决策（ADR 摘要）

| 决策 | 选择 | 放弃的方案 | 原因 |
|---|---|---|---|
| 动态字段存储 | 记录 JSONB 单列 | 动态加列 / 纯 EAV | 零 DDL、读写简单；查询靠表达式索引补偿；千万行再上值列存 |
| 查询编译 | 自研 DSL→AST→SQL | Calcite / JPA Specification | Calcite 擅长老 SQL/联邦查询，不为封闭 DSL 设计；JPA 生不出好的 JSONB SQL |
| 协同 | 单元格 op + 乐观锁 + change_log | 自研 OT / Yjs | 覆盖 95% 场景，成本 1/5；Java 无 Yjs 绑定 |
| 权限 | 应用层查询改写 | 全靠 Postgres RLS | RLS 有 owner 绕过、连接池串会话陷阱，且字段级权限仍要应用层裁剪 |
| 前端数据层 | 自建 RecordStore | VTable 内置分页/排序 | VTable 内置分页是前端切片，排序是前端行为，与后端分页天然冲突 |
| 视图类型 | 先只做网格 + 服务端筛选 | 一次做看板/日历/甘特 | 视图是"同一份数据的另一种渲染"，先保证数据层对 |

## 9. 容量与性能目标

| 指标 | 目标（8C16G 单实例） |
|---|---|
| 列表首屏（200 行 × 30 字段，含筛选） | P95 < 150 ms |
| 单元格编辑提交 | P95 < 100 ms（前端感知 < 50 ms） |
| 单表 100 万行筛选+排序首屏 | P95 < 500 ms |
| 聚合（20 万行，group by 1 列） | P95 < 1 s |
| 导出 100 万行 CSV | < 60 s |
| 在线人数 / 并发编辑 | 5k 在线 / 单表 200 人同时编辑 |
| 单库数据量（不分区） | < 5000 万条记录；超过按 `hash(datasheet_id)` 分区 |

压测方式与优化顺序（索引 → 查询改写 → 缓存 → 分区 → 拆库）见 01 §13。

## 10. 部署形态

**私有化（大多数企业内部的选择）**

```yaml
# docker-compose 骨架：7 个容器
nginx            # TLS + 静态资源 + /api 反代
app              # Spring Boot（2~3 副本）
web              # Nginx 托管前端静态产物
postgres         # 主库（+ 只读副本，可选）
redis            # 缓存 + Pub/Sub
minio            # 附件
backup           # 每日 pg_dump + WAL 归档
```

**K8s**：`app`（HPA 3~10）、`ws`（单独 Deployment，长连接粘性）、`postgres`（云 RDS 或 Patroni）、`redis`（哨兵）、`minio`。把"协同连接数"和"HTTP QPS"分开扩容，否则长连接会把 HTTP 实例的线程/内存吃光。

**企业内落地的三个硬要求**：SSO（OIDC/LDAP/企业微信/飞书）、数据不出内网（无外网依赖，字体/图标/CDN 全本地化）、备份可演练（每月一次真实恢复演练，而不只是备份成功）。

## 11. 里程碑（详细排期见 04）

| 阶段 | 周期 | 交付 | 验收 |
|---|---|---|---|
| **S0 技术验证** | 2 周 | 3 个 spike：VTable 30 万行渲染 + 编辑、PG 100 万行 JSONB 筛选、WS 协同 demo | 三个指标达标，否则换方案 |
| **P0 MVP** | 8 周 | 单表、10 种字段、网格视图、筛选排序分组、单元格编辑、基础权限、CSV 导入导出、审计 | 单表 5 万行可用，10 人内测 |
| **P1 协作版** | 8 周 | 实时协同、冲突 UI、行/字段级权限、关联/查找/汇总、看板视图、历史回滚 | 单表 50 万行，200 人试点 |
| **P2 企业版** | 8 周 | 公式、自动化/Webhook、OpenAPI、SSO、多租户、仪表盘、千万行优化 | 全公司推广，SLA 99.9% |

人力基线（不是绝对）：**后端 2~3 + 前端 1~2 + 全栈/架构 1 + QA 1 + PM/设计 0.5**。26 周做到 P2，期间必须留 15~20% 缓冲给"数据迁移和用户抱怨"。

## 12. 风险清单（按杀伤力排序）

| # | 风险 | 表现 | 对冲 |
|---|---|---|---|
| 1 | 低估数据层工作量 | 以为 VTable 带数据层，结果前端写崩 | S0 就验证分页/编辑链路；明确 VTable 只是渲染器 |
| 2 | 协同一致性 | 冲突丢数据、重连后状态错乱 | 先做 op 日志 + 幂等 + 增量重放，CRDT 只用于富文本且放 P2 |
| 3 | 千万行动态字段查询 | 筛选慢、GIN 写放大、深分页 | 表达式索引 + keyset + 值列存，按档灰度（01 §5、§14） |
| 4 | 权限越权 | 导出口/API/WS 漏校验，字段级只在前端隐藏 | 所有入口共用 PermissionService；集成测试专测越权 |
| 5 | 公式引擎被当成小功能 | 用户要 300 个 Excel 函数 | 先做 30 个高频函数 + 明确"不支持清单"，按需扩 |
| 6 | 导入脏数据 | 类型不匹配、重复主键、超大文件 OOM | 预览 + 错误行报告 + 后台任务 + 流式解析 |
| 7 | License 踩坑 | 想抄 APITable 代码（AGPL-3.0，网络服务有传染性）；SeaTable 的 dtable-server 是专有许可 | 只借鉴架构思路不复制代码；商用前过一遍 License |
| 8 | 组织阻力 | "为什么不直接用飞书/Excel" | 提供一键导入、模板、Excel 公式兼容、只读嵌入 |
