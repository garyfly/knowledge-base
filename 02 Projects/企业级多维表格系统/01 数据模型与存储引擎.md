# 01 数据模型与存储引擎（PostgreSQL）

> 这篇回答一个问题：**多维表格的数据到底怎么存，才能既支持用户随时加字段，又能在百万行上跑筛选、排序、分组和公式。**
>
> 结论先行：
> 1. **元数据强类型、数据 JSONB**：表/字段/视图用普通关系表存，记录的业务数据塞进 `record.data` 一列 JSONB。动态加字段 = 插一行元数据，不做 `ALTER TABLE`。
> 2. **值列存（`record_cell`）是可选的第二存储**，只在数据量或查询形态逼得你必须有时才启用，双写维护。不要一上来就上 EAV。
> 3. **筛选/排序/分组都编译成 SQL**，不捞回应用层过滤；深分页一律 keyset，不用 offset。

---

## 1. 为什么不是「一个表一套物理表结构」

用户加一个字段，如果对应的是一次 `ALTER TABLE ... ADD COLUMN`：

| 问题 | 具体表现 |
|---|---|
| DDL 膨胀 | 一个空间 500 张表 × 平均 40 字段 = 2 万个列，PG 的系统表（`pg_attribute`）和 schema 同步都会被拖慢 |
| 变更成本 | 改字段类型、删字段、改选项顺序，都要 DDL + 数据回填，出错不可回滚 |
| 多租户隔离 | 每个租户一套 DDL，升级脚本要按租户跑，运维复杂度指数上升 |
| 权限/审计 | 列的元信息（谁能看、改过没）散落到数据库元数据里，应用层拿不到统一视图 |

所以主流实现都是**元数据驱动**的：字段定义是一行数据，记录是一个 JSON 文档（APITable / NocoDB / 飞书多维表格走这条路）；另一派是把字段直接落成物理列（Baserow / Teable 这类「真 PG 表」路线），查询最爽但字段一多就是 DDL 灾难。本方案选前者，理由见 §5 的三条路线对比。

## 2. 四层数据模型

```
空间(space / 租户隔离边界)
 └─ 数据表(datasheet)           ← 用户眼里的"一张表"
     ├─ 字段(field)            ← 元数据，定义类型/选项/公式/关联
     ├─ 视图(view)             ← 筛选/排序/分组/字段顺序/列宽，纯配置
     └─ 记录(record)           ← 业务数据 + 协同版本号 + 软删除
```

再往下一层是**横切能力**，不属于任何一张表：变更日志（协同 + 审计）、附件、评论、自动化、权限。

## 3. 元数据表 DDL

```sql
-- 空间：权限、计费、备份的最小隔离单位
create table space (
  id          bigint primary key,
  name        text not null,
  owner_id    bigint not null,
  plan        text not null default 'internal',
  created_at  timestamptz not null default now()
);

-- 数据表
create table datasheet (
  id               bigint primary key,
  space_id         bigint not null references space(id),
  name             text not null,
  description      text,
  icon             text,
  primary_field_id bigint,                    -- 主字段（首列），冗余避免 join
  record_count     bigint not null default 0, -- 近似值，异步维护，勿当精确数
  created_by       bigint not null,
  created_at       timestamptz not null default now(),
  updated_at       timestamptz not null default now(),
  deleted_at       timestamptz
);
create index idx_datasheet_space on datasheet (space_id) where deleted_at is null;

-- 字段：多维表格的全部"形状"都在这里
create table field (
  id           bigint primary key,
  datasheet_id bigint not null references datasheet(id),
  name         text not null,
  type         text not null,          -- 见 §4 类型清单
  property     jsonb not null default '{}'::jsonb,
  -- property 里的典型内容：
  --   单/多选：{"options":[{"id":"o1","name":"高","color":"red"}]}
  --   数字：  {"precision":2,"format":"currency","currency":"CNY"}
  --   日期：  {"format":"yyyy-MM-dd","timeZone":"Asia/Shanghai"}
  --   关联：  {"datasheetId":"123","multiple":true,"symmetricFieldId":null}
  --   公式：  {"expression":"SUM({f1}, {f2}) * 0.1"}
  --   自动编号：{"prefix":"TASK-","digits":4}
  is_primary   boolean not null default false,
  required     boolean not null default false,
  hidden       boolean not null default false,   -- 表级隐藏，数据仍在
  sort_order   int not null,
  created_at   timestamptz not null default now(),
  deleted_at   timestamptz
);
create unique index uk_field_name on field (datasheet_id, lower(name)) where deleted_at is null;
create index idx_field_ds on field (datasheet_id) where deleted_at is null;

-- 视图：一份配置，零份数据
create table view (
  id           bigint primary key,
  datasheet_id bigint not null references datasheet(id),
  name         text not null,
  type         text not null default 'grid',   -- grid/kanban/calendar/gantt/form/gallery
  config       jsonb not null default '{}'::jsonb,
  -- {"filters":{"conjunction":"and","conditions":[...]},
  --  "sorts":[{"fieldId":"f2","desc":true}],
  --  "groups":[{"fieldId":"f9"}],
  --  "hiddenFieldIds":["f7"], "fieldOrder":["f1","f2"],
  --  "frozenFieldCount":1, "rowHeight":"medium", "columnWidths":{"f1":160},
  --  "kanban":{"groupFieldId":"f9"}}
  is_default   boolean not null default false,
  created_by   bigint,
  created_at   timestamptz not null default now()
);
```

> 视图配置里**不存数据快照**。视图 = 查询条件，随看随算；需要固定结果时用"快照/归档表"功能，那是另一个产品能力。

## 4. 字段类型与 JSONB 编码约定

数据编码的第一原则：**JSON 类型必须与字段语义一致**，这样 `@>` 包含查询和表达式索引才能用上，也免去到处 `::numeric` 转换。

| 字段类型 | JSONB 编码 | 例子 |
|---|---|---|
| 文本 / 多行文本 | string | `"调研竞品"` |
| 数字 / 货币 / 百分比 | number | `42.5` |
| 日期 / 日期时间 | number（epoch ms，UTC） | `1763395200000` |
| 复选框 | boolean | `true` |
| 单选 | string（选项 id） | `"o1"` |
| 多选 | array\<string\>（选项 id） | `["o1","o3"]` |
| 成员 / 协作人 | array\<number\>（用户 id） | `[1001,1002]` |
| 附件 | array\<object\> | `[{"token":"att_xxx","name":"a.pdf","size":1024,"mime":"application/pdf"}]` |
| 关联（link） | array\<number\>（对方记录 id） | `[9001,9002]` |
| 等级 / 评分 | number | `4` |
| 自动编号 | number + 元数据里的前缀 | `1001` |
| 公式 / 查找 / 汇总 | 计算结果（物化） | `1234.5` |
| 创建时间 / 创建人 / 更新时间 / 更新人 | number | 系统写入，只读 |

约定：
- **空值统一为「key 不存在」**，不写 `null`。`{"f1": null}` 会让 `is empty` 判断和 GIN 索引都变复杂。
- 选项用 **id 不用显示名**：改选项名不需要回填历史数据；排序按 `property.options` 里的顺序做映射。
- 时间统一存 epoch ms：跨时区比较不用管 collation，也省去 `to_char`。
- 文本长度上限在应用层卡（比如 64 KB），**不要用 PG 的 `text` 无限制兜底**——一条 10 MB 的 JSONB 会拖垮整个 `record` 的读放大。

## 5. 记录存储：三条路线，一档一档上

```sql
create table record (
  id           bigint      not null,            -- snowflake，全局有序
  datasheet_id bigint      not null,
  data         jsonb       not null default '{}'::jsonb,
  rank         text        not null,            -- 手动排序用的分数索引（见 §6）
  version      bigint      not null default 1,  -- 协同乐观锁
  created_by   bigint      not null,
  updated_by   bigint      not null,
  created_at   timestamptz not null default now(),
  updated_at   timestamptz not null default now(),
  deleted_at   timestamptz,                     -- 回收站
  primary key (datasheet_id, id)
);
```

### 三条路线

| 路线 | 结构 | 优点 | 致命短板 | 适用 |
|---|---|---|---|---|
| **A. 纯 JSONB** | `record.data` 一列 | 写入/读取一次搞定，实现最快，天然支持任意字段数 | 排序、范围筛选、聚合都靠表达式索引或全表扫描；GIN 只加速 `@>` 等值/包含 | 单实例 < 200 万行 |
| **B. JSONB + 值列存** | 上面再加 `record_cell`（一行一个单元格，类型化列） | 排序/范围/聚合走 B-tree，索引可控；可按字段建索引 | 双写一致性、写放大（一条记录 = N 行）、删除清理 | 200 万 ~ 5000 万行 |
| **C. EAV 单轨** | 只存 `record_cell`，拼装靠 join | 索引最灵活 | 读一条记录要 N 行回拼；首屏/导出/关联查询全是 join，Java 侧聚合成本高 | 不推荐作为主存储 |

**本书推荐：A → B 渐进。** 先按 A 上线，把 `record_cell` 的写入路径（双写队列）和查询编译器预留好接口；等某个空间真的出现"百万行 + 多字段排序"再打开 B，而不是一开始就背上双写的复杂度。

### 值列存 DDL（B 档）

```sql
create table record_cell (
  datasheet_id bigint not null,
  field_id     bigint not null,
  record_id    bigint not null,
  num_value    numeric,
  text_value   text,
  ts_value     timestamptz,
  bool_value   boolean,
  ref_id       bigint,          -- 关联字段：被关联记录
  arr_value    jsonb,           -- 多选/成员/附件：数组
  primary key (datasheet_id, field_id, record_id)
);

-- 数值/日期范围筛选与排序
create index idx_cell_num on record_cell (datasheet_id, field_id, num_value)
  where num_value is not null;
create index idx_cell_ts  on record_cell (datasheet_id, field_id, ts_value)
  where ts_value is not null;
-- 文本前缀/等值（注意：中文排序要 collation，见 §6）
create index idx_cell_text on record_cell (datasheet_id, field_id, text_value)
  where text_value is not null;
-- 反向：按记录批量取全部单元格（列表页首屏）
create index idx_cell_record on record_cell (datasheet_id, record_id);
```

写入方式：记录写入事务内 `insert ... on conflict do update`，或大促/导入时先落 `record`、由异步任务批量 upsert（牺牲秒级一致性换吞吐，**ACL 和视图查询必须能容忍延迟**，所以只对"导入/批量更新"这条路开异步）。

## 6. 查询编译：筛选 DSL → SQL

### 6.1 筛选 DSL（前后端契约）

```json
{
  "conjunction": "and",
  "conditions": [
    { "fieldId": "f_1001", "op": "eq", "value": "o1" },
    { "fieldId": "f_1002", "op": "gt", "value": 100 },
    { "fieldId": "f_1003", "op": "contains", "value": ["研发"] },
    { "fieldId": "f_1004", "op": "isNotEmpty" }
  ]
}
```

算子集合（按类型开放，不是所有类型都支持所有算子）：`eq / ne / gt / gte / lt / lte / between / in / notIn / contains / notContains / startsWith / endsWith / isEmpty / isNotEmpty / isAnyOf（多选）`。

### 6.2 编译到 JSONB（A 档）

```sql
-- eq：GIN 直接吃
(data @> '{"f_1001":"o1"}'::jsonb)

-- gt（先锁类型，避免脏数据 cast 报错）
(jsonb_typeof(data->'f_1002') = 'number' and (data->>'f_1002')::numeric > 100)

-- 多选包含
(data->'f_1003' @> '["研发"]'::jsonb)

-- 非空
(data ? 'f_1004')
```

参数化：`data @> ?::jsonb`、`(data->>'f_1002')::numeric > ?`，**绝不拼字符串**（SQL 注入 + 执行计划复用）。字段 id 只允许出现在 `->` 的常量位置，且必须来自本表字段白名单校验，不能用用户输入直接拼。

### 6.3 编译到值列存（B 档）

```sql
-- 条件变成 EXISTS 子查询，或先按字段取候选集再 JOIN
select r.* from record r
where r.datasheet_id = 123 and r.deleted_at is null
  and exists (select 1 from record_cell c
              where c.datasheet_id = 123 and c.record_id = r.id
                and c.field_id = 1002 and c.num_value > 100)
order by r.rank
limit 201;
```

字段多、条件多时，`EXISTS` 叠加会让优化器挑错计划。两个经验：
1. **单字段条件优先走 `record_cell` 直接驱动**：`select record_id from record_cell where datasheet_id=? and field_id=? and num_value > ?`，再 `join record using (datasheet_id, id)`，让它走索引扫描。
2. **组合条件超过 3 个**时，考虑把视图的筛选条件下沉成"物化结果表"（定时刷新），企业内表格的视图本来就不需要秒级一致。

### 6.4 排序

| 排序键 | 做法 |
|---|---|
| 默认（手动排序） | `order by rank, id`（rank 是分数索引，见 §7） |
| 数字/日期 | `order by (data->>'f')::numeric` / 值列存 `c.num_value` |
| 文本 | `order by (data->>'f') collate "zh-x-icu"`，需要 ICU collation：`create collation "zh-x-icu" (provider = icu, locale = 'zh-Hans')` |
| 单选 | 按 `property.options` 的顺序编译成 `case data->>'f' when 'o1' then 1 when 'o2' then 2 ... end`（选项少，可接受） |
| 多字段排序 | 依次追加 `, ...`，最后一个永远是 `id`，保证分页稳定 |

## 7. 分页与手动排序

### 深分页：只用 keyset

```sql
-- 第一页
select * from record
where datasheet_id = 123 and deleted_at is null
order by rank, id limit 201;
-- 后续页：cursor = (last_rank, last_id)
select * from record
where datasheet_id = 123 and deleted_at is null
  and (rank, id) > ('a0V', 9001)
order by rank, id limit 201;
```

offset 到 10 万行时 PG 要扫描并丢弃 10 万行，P95 直接进秒级；keyset 恒定为索引 seek。

### 手动排序（拖拽）用分数索引，不用整数序号

整数序号在"拖到两行之间"时要把后面所有行 +1，一行拖拽写 N 行。用**字符串分数索引**（lexicographic，`a0` < `a0V` < `a1`）或小数：

```sql
-- 插到 a0 和 a1 之间
update record set rank = 'a0V', version = version + 1 where id = ?;
```

相邻 key 之间插满（比如连续插 20 次）时触发一次区间重排（后台任务把该区间重新生成均匀 key）。这是 Figma/Notion 类产品通用的做法。

### 总数

`count(*)` 在百万行上是持续开销。策略：
- `datasheet.record_count` 维护近似值（写入时 ±1，或定时 `reltuples` 采样）；
- 前 3 页返回精确 `total`（`count(*) over ()` 走同一索引范围）；
- 之后只返回 `hasMore` / `nextCursor`，不返回总数。

## 8. 聚合、分组与统计

看板视图、图表、汇总行都要 `GROUP BY`：

```sql
select (data->>'f_status') as status, count(*), sum((data->>'f_amount')::numeric)
from record
where datasheet_id = 123 and deleted_at is null
  and (data->>'f_owner') = '1001'
group by 1;
```

注意：
- **先筛选后聚合**，`GROUP BY` 的字段一定要在 `WHERE` 之后才可能命中索引。
- 分组值可能是选项 id，**结果集回前端时由元数据翻译成显示名**（不要在 SQL 里 join 元数据）。
- 聚合查询单独限流 + 限时（`statement_timeout` 2s），失败降级为"请缩小筛选范围"，不要让一个看板拖垮主库。

## 9. 索引与分区策略

| 场景 | 索引 |
|---|---|
| 列表页（默认视图） | `(datasheet_id, rank) where deleted_at is null` |
| 单字段等值筛选 | GIN `data jsonb_path_ops`（A 档）或 `(datasheet_id, field_id, value)`（B 档） |
| 文本搜索 | `pg_trgm` 的 GIN 索引，或 `to_tsvector`（中文分词用 `zhparser` 或 `pg_jieba`，企业内一般直接用 `pg_trgm` 模糊匹配够用） |
| 关联字段反查 | `record_link (field_id, to_record_id)`（见 §10） |
| 软删除过滤 | 部分索引带 `where deleted_at is null`，体积小一半 |

分区：`record` 按 `hash (datasheet_id)` 分 16 片，单表超过 5000 万行时收益明显；**但分区会限制唯一索引必须带分区键**，所以主键用 `(datasheet_id, id)`。表数少、数据量不大时**别分区**，运维成本大于收益。

### 9.1 JSONB 索引的四条边界（PostgreSQL 18）

这四条决定了"什么时候必须上值列存"，写方案时先记住：

1. **GIN 只覆盖等值和包含**：支持 `@>`、`?`、`?|`、`?&`、`@?`、`@@`，**不支持范围比较和排序**。`(data->>'due')::timestamptz > now()` 这种写法 GIN 帮不上忙，必须表达式索引或 STORED 生成列。
2. **`jsonb_path_ops` 更小更快但更窄**：只支持 `@>`、`@?`、`@@`；`{"a": {}}` 这类无值结构不产生索引项，相关查询会退化成全索引扫描。要"键存在"判断（`?`）就得用默认的 `jsonb_ops`。
3. **JSONB 更新是整行行锁**：改一个字段要重写整个 JSONB。单行 JSON 越大，写冲突越重、WAL 越多 → **控制单条记录体积**（长文本/附件元数据别塞进来），热点记录做合并写。
4. **生成列注意 STORED**：PG 18 起虚拟生成列是默认形态，但**逻辑复制只支持 STORED 生成列**；要做 CDC / 从库同步，务必显式写 `STORED`。

```sql
-- 热点字段的两种加速写法
create index idx_due on record (((data->>'f_due')::timestamptz)) where deleted_at is null;  -- 表达式索引
alter table record add column f_due_ts timestamptz generated always as
  ((data->>'f_due')::timestamptz) stored;                                                    -- 生成列（可建普通索引）
create index idx_due2 on record (f_due_ts) where deleted_at is null;
```

## 10. 关联 / 查找 / 汇总

关联字段（link）是双向的，用独立边表，一条边两行或一行的对称写：

```sql
create table record_link (
  field_id      bigint not null,   -- 发起方字段
  from_record   bigint not null,
  to_record     bigint not null,
  symmetric_field_id bigint,       -- 对方表上的对称字段（反向关联）
  primary key (field_id, from_record, to_record)
);
create index idx_link_to on record_link (field_id, to_record);
```

- **查找（lookup）**：读对方记录的某个字段值，物化到本记录 `data` 里（对方字段变更时触发重算）。
- **汇总（rollup）**：在关联边集合上做 count/sum/avg/min/max，同样物化。
- 物化的代价是**链路一致性**：A 改 → 触发 B 重算 → B 如果又汇总到 C，需要级联。实现上用"变更事件 + 依赖图"（见 `03 公式与计算引擎`），并接受**最终一致**（秒级延迟），前端显示"计算中"。

## 11. 字段变更时的数据迁移

| 操作 | 做法 |
|---|---|
| 加字段 | 只插元数据，零数据迁移（新字段在 `data` 里不存在 = 空） |
| 改字段名 | 只改 `field.name`（数据里存的是 id，不受影响） |
| 改字段类型 | **不在原字段上改**。新建字段 + 后台迁移任务 + 切换 + 删旧字段；或标记 `migrating` 状态只读 |
| 删字段 | 软删元数据；`data` 里的旧 key 保留（回滚需要），由一个"垃圾回收"任务在 N 天后 `data - 'f_xxx'` 批量清理 |
| 改选项顺序/名称 | 只改 `property.options`，数据里是 id，无迁移 |
| 唯一性约束 | 应用层校验 + 值列存上的唯一索引（A 档下 GIN 不支持唯一，得靠 B 档或应用层锁） |

## 12. 导入导出

| 方向 | 做法 | 关键点 |
|---|---|---|
| 导入 CSV/XLSX | 流式读（EasyExcel / FastExcel），按字段名映射，逐行 `COPY` 或批量 `insert ... values`（每批 1000 行） | 类型推断与错误行报告；一文件一个事务（失败整体回滚）或分批提交 + 错误明细；导入 100 万行用后台任务 + 进度条，不走同步 HTTP |
| 导入时建字段 | 允许"首行是表头，自动建字段"，类型推断走预览页确认，别自动猜 | 推断错比让用户选更烦 |
| 导出 CSV | PG `COPY (select ...) TO STDOUT WITH CSV HEADER` 直接流式回响应 | 中文 Excel 兼容要 UTF-8 BOM（否则乱码） |
| 导出 XLSX | SXSSF 流式写，行数 > 50 万提示改用 CSV | XLSX 单表 104 万行上限、内存按行缓冲 |
| 导出快照 | 走只读副本，避免大导出打满主库 | 导出任务并发放一个信号量 |

## 13. 性能目标与压测方法

先定数字，再谈优化：

| 指标 | 目标（企业内，单实例 8C16G） |
|---|---|
| 列表首屏（200 行 × 30 字段，带筛选） | P95 < 150 ms |
| 单元格编辑提交 | P95 < 100 ms |
| 单表 100 万行、单字段筛选 + 排序首屏 | P95 < 500 ms（A 档需表达式索引，B 档天然达标） |
| 聚合（20 万行，group by 1 列） | P95 < 1 s |
| 导出 100 万行 CSV | < 60 s（流式，不占内存） |
| 并发编辑 | 单表 200 人同时在线，P99 写入 < 300 ms |

压测方法：`pgbench` 自定义脚本 或 JMeter 打后端；先用 `generate_series` 造 100 万行 JSONB 记录，跑真实筛选组合，看 `EXPLAIN (analyze, buffers)` —— **优化依据是执行计划和 buffer 命中率，不是直觉**。

## 14. 演进路线（别一次做完）

1. **P0**：A 档纯 JSONB + 表达式索引（只给 3~5 个高频字段）+ keyset 分页。
2. **P1**：加 `record_cell` 双写，仅对"用户标记为可排序/可筛选"的字段建行；查询编译器按"字段是否已列存"决定走哪条路径。
3. **P2**：分区、只读副本承担列表读、导出独立任务队列、超大表迁到独立实例。

> 每一档都保留一个开关（`datasheet.storage_mode = A|B`），按表灰度，出问题能退回去。这条比任何性能优化都重要。
