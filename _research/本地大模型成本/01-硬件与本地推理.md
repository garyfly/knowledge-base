### B3. 64GB 机型到底能分多少显存给 GPU（关键）

这是 64GB 版本最容易被忽略的限制，也是"能不能跑 100B 级"的答案。

**Linux（唯一有实测的路线）**

| 项目 | 数值 | 来源 |
|---|---|---|
| GTT 默认上限 | **约系统内存的 50%** → 64GB 机器约 **28 GiB** | [AMD ROCm 官方文档](https://rocm.docs.amd.com/en/docs-7.2.0/how-to/system-optimization/strixhalo.html) |
| 64GB Minisforum N5 MAX 实测 | **固定 VRAM 约 2 GiB + GTT 约 28 GiB = GPU 默认看到约 30 GiB** | [Level1Techs 评测](https://forum.level1techs.com/t/nas-review-notes-minisforum-n5-max-amd-strix-halo/251183)（经 guide 转述） |
| 解锁方法 | `amdgpu.gttsize=` / `ttm.pages_limit=` 内核参数；AMD 提供 `amd-ttm --set 52` 工具 | [ROCm 文档](https://rocm.docs.amd.com/en/docs-7.2.0/how-to/system-optimization/strixhalo.html) |
| AMD 官方建议 | **BIOS 里 VRAM 设到最小（0.5GB），把共享内存交给 GTT 调大** | 同上 |
| 版本要求 | **内核 ≥ 6.18.4**（含 KFD 修复）；ROCm 7.11.0 为官方支持组合 | 同上 |

**Windows**

| 项目 | 数值 | 来源 |
|---|---|---|
| 分配机制 | Adrenalin 25.8.1 起有 **Variable Graphics Memory (VGM)**，128GB 机器最高可设 96GB | [guide WINDOWS_START](https://github.com/hogeheer499-commits/strix-halo-guide/blob/main/WINDOWS_START.md) |
| VGM 挤占系统内存 | 128GB 机器设 VGM=96GB 时，**Windows 只剩约 31.6GB 可用** | 社区报告（Adrenalin 26.5.2） |
| **已知大模型加载 bug** | 128GB + VGM 96GB 下，**加载约 64GB 以上的模型失败**（LM Studio #1790，2026-04 开，2026-10 仍 open，AMD 未确认） | [lmstudio-bug-tracker#1790](https://github.com/lmstudio-ai/lmstudio-bug-tracker/issues/1790) |
| 64GB 机器的 VGM 上限 | **未查到确切值**（按"最多到一半"的惯例推算约 32GB） | — |

**→ 64GB 到底能跑多大模型**

| 模型体积 | 64GB 能否全 GPU 常驻 | 说明 |
|---|---|---|
| ≤ 20 GB（Qwen3-30B-A3B Q4、Qwen3.8-27B dense） | ✅ 舒服 | 默认 30GiB 留 10GB 给上下文/OS |
| 20–30 GB | ✅ 可以 | 需留足 KV cache 余量 |
| 40–50 GB（Qwen3-Coder-Next 48.5GB） | ⚠️ 紧 | **必须改内存分割**，否则默认 30GiB 装不下；改完 OS 只剩十几 GB |
| ~52.5 GB（Qwen3.5-122B-A10B Q3_K_S） | ⚠️ Framework 官方 64GB 档推荐，但是厂商声明，未独立复现 | 需把 GTT 调到接近极限 |
| **63.4 GB（gpt-oss-120b MXFP4）** | ❌ **跑不了** | 即使 64GB 全给 GPU 也没空间放 KV cache + OS。这是硬结论 |
| ≥ 90 GB（DeepSeek V4 Flash 284B） | ❌ 跑不了 | 需 128GB |

**会 OOM 的 100B 级 MoE 清单（64GB 机器）：** gpt-oss-120b（63.4GB）、Llama 4 Scout 109B（61GB，边缘）、Nemotron 3 Super 120B-A12B（64.5GB）、Qwen3.5-122B-A10B Q3（52.5GB，极限可试）、GLM-4.5-Air、任何 Q4 的 100B+ 模型。

> 一句话：**64GB 是"30B 级专用机"，128GB 才是"120B 级入门机"。** 想跑 gpt-oss-120b 请直接上 128GB。

### C2. ROCm 对 gfx1151 的支持程度 → **Linux 几乎是必须的**

| 事项 | 现状 |
|---|---|
| ROCm 官方支持 | **已支持**，且 AMD 专门写了 [Strix Halo 优化文档](https://rocm.docs.amd.com/en/docs-7.2.0/how-to/system-optimization/strixhalo.html)。ROCm 7.11.0 + 内核 ≥6.18.4 是官方推荐组合；7.2.0 在 OEM 内核上也可 |
| 发行版 | **Fedora 43 / Ubuntu 26.04 / Arch 原生打包**已含必需内核修复 |
| 实测路线 | 指南全部一手实测都在 **Ubuntu 24.04 / Fedora 43 原生 Linux** 上 |
| 性能对比 | **decode（tg）Vulkan RADV/AMDVLK 普遍更快；prefill（pp）ROCm 7.x 更快**。例：Qwen3-Coder-Next Q6 上 Vulkan AMDVLK 38.65 tg vs ROCm 7.x 约 33；但 pp 上 ROCm ~502 vs AMDVLK 358 |
| **AMDVLK 陷阱** | 装了 AMDVLK 会**静默劫持 RADV**，实测 pp 掉 39%（1080→660）且无任何报错。**新手规则：只用 RADV，别装 AMDVLK** |
| Windows ROCm 限制 | AMD 官方限制页：**仅 PyTorch、不支持训练、仅 Python 3.12、官方只保证 batch size 1**，还要关 Smart App Control 和 Defender Application Guard |
| WSL2 | Adrenalin 26.2.2 + ROCm 7.2.1 起官方支持 ROCDXG；但实测比原生 Linux 慢（44.05 vs 61.52 t/s） |

**→ 结论：想要"好用"，装 Linux。Windows 能跑，但慢、坑多、大模型加载有未修复 bug。**

### C3. 和 CUDA 生态的差距

| 方面 | 差距 |
|---|---|
| **vLLM** | gfx1151 上基本不可用/极不稳定。指南有专门的 [ROCM_VLLM_BUGWATCH.md](https://github.com/hogeheer499-commits/strix-halo-guide/blob/main/ROCM_VLLM_BUGWATCH.md) 跟踪 bug。这意味着**没有生产级高并发 serving** |
| **微调** | 理论可跑（Unsloth ROCm 路线已跑通一步 SFT + GGUF 导出），但：**bitsandbytes 到 0.49.2 在所有 AMD GPU 上有 4bit 解码 NaN bug**，必须用 0.50.0.dev0 预发布版；Axolotl/LLaMA-Factory 无 gfx1151 证据。**微调能力≈没有** |
| **bitsandbytes / 4bit** | 如上，只能用 dev 版，风险自担 |
| **图像/视频生成** | ComfyUI 可用但慢：Flux.2 在 Framework Desktop 上约 **10 分钟/张**，DGX Spark 约 2 分钟（Tweakers 测试）；Wan 2.2 14B 720p 41 帧约 2000 秒 |
| **语音** | LM Studio Windows 上 AMD **语音模式完全不可用**（只有 CUDA 语音识别引擎，#2341） |
| **量化工具** | AMD Quark 可在机器上量化（35B 模型需 128GB 机器，AMD 官方博客 2026-09-25） |
| **生态本质** | 一切"加速库"（FlashAttention 变体、Triton kernel、TensorRT、各种 fused op）都要等 AMD 适配。**能用 ≠ 好维护** |

### C4. 噪音、散热、稳定性口碑

**正面：**
- 120W 跑 120B 模型时 36–41 dBA，蒸发腔双风扇设计被 ServeTheHome 评为"安静"
- Minisforum/MS-S1 满载 >50 dBA，偏吵（heise）
- 天钡 NEX 395 用均热板+铜鳍片+独立 M.2 风扇，140W 释放

**坑（有据可查）：**
1. **Beelink GTR9 Pro 的 Intel E610 万兆网卡在负载下断连甚至死机**——ComputerBase 报道跑本地 LLM（LM Studio, Llama 4 Scout）可复现崩溃，需拔电源才恢复；v2.2 板换成 Realtek RTL8127 解决。**买前必须确认板卡版本（GTRPR05 vs GTRPR07）**
2. **BIOS 更新渠道差异大**：Framework/HP 有 LVFS（fwupd）自动更新；Beelink 只有手动下载目录；**GMKtec 官网连 BIOS 文件都不提供**
3. **内存焊死不可升级**：所有 64GB 机型都是板载 LPDDR5X，**买了就定死**。选错容量无法补救
4. **保修条款普遍排除商用**：GMKtec/Beelink/Minisforum 欧洲条款均以不同措辞排除商业使用
5. **USB4 eGPU 不稳定**：Bosgame M5 反复死机，M.2 转 OCuLink 才行
6. 二手/矿卡对比下，395 的稳定性优势是真实的（无显存、无独立供电、单芯片）

## E. 给这位用户的最终建议

**买 64GB 的前提条件（三条全满足才值）：**
1. 你的主力模型是 **30B 级 MoE**（Qwen3-30B-A3B / Qwen3-Coder-30B，100 t/s）或 **27B dense**（13–23 t/s）
2. 你**不打算跑 gpt-oss-120b 或任何 100B+ 模型**（64GB 物理上做不到）
3. 你愿意**装 Linux** 并接受折腾（Windows 能跑但慢、有未修复 bug）

**不买 64GB 的情况：**
- 想跑 gpt-oss-120b → 直接 128GB（¥22,999 起），别省这 1 万
- 需要微调、vLLM 高并发、图像视频生成 → 买 3090/5090（CUDA 生态）
- 每周用量 < 10 小时 → 云 GPU（¥1.3/h）

**"划不划算"的量化答案：**
- **纯算力/¥：不划算。** 单张二手 3090（¥9,200）在 24GB 以内的模型上比 395 快 1–3 倍，价格更低。
- **算力/瓦：非常划算。** 120W 跑 100 t/s 的 30B 模型，能效比是 3090（350W）的 4 倍以上，比双 3090（700W）高一个数量级。
- **每 GB 可用内存/¥：中等。** ¥406/GB（可用口径），比 2026 年的 3090（¥383/GB）略贵，但含整机。
- **2026 年特殊变量：** 显存危机让 3090/5090 涨幅（60–119%）远超 395（板载 LPDDR5X 涨幅较小），**395 的相对性价比在 2026 年反而是近年最好的**。
